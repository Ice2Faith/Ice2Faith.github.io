### 软件工程的定义

- 软件工程，指应用计算机科学、数学及管理科学等原理
- 以工程化的原则和方法来解决软件问题的工程
- 目的是，提高软件生产率、提高软件质量、降低软件成本

### 软件过程模型（软件生命周期模型）

- 使软件生命周期的各项任务更够有序的按照规程进行
- 对这些任务进行规程约束的工作模型
- 就叫做，软件过程模型
- 也叫做，软件生命周期模型

#### 软件生命周期

- 需求分析
- 软件设计
- 软件开发
- 运行维护
- 消亡淘汰

#### 瀑布模型

- 依次从上一个阶段到下一个阶段运行
- 严格按照顺序执行
- 每一个阶段都要激励性检查和确认
- 生命周期
    - 需求分析
    - 系统设计
    - 程序设计
    - 编码实现
    - 单元测试
    - 集成测试
    - 系统测试
    - 运行维护
- 适用场景
    - 需求非常明确的
    - 一般常见于军工项目，局部保密的情况下，需求就必须非常明确
- 优点
    - 利于组织，便于管理
- 缺点
    - 需求完整、正确往往很难确定
    - 用户需要很长时间才能看到系统
    - 纠错、变更代价巨大
    - 每个阶段很难完全解决本阶段的工作

#### 原型模型（快速原型模型）

- 根据需求，快速开发一个原型
- 实现关键问题、反映大致面貌、展示部分功能
- 仅供多轮的原型之后，需求逐渐清晰明确
- 再开始实际的编码实现
- 生命周期
    - 需求分析
    - 系统设计
    - 程序设计
    - 原型开发
        - 不满意，重新回到，需求分析
        - 前三个阶段中都可能穿插原型开发
        - 部分情况，可能也涉及一部分编码
    - 编码实现
    - 单元测试
    - 集成测试
    - 系统测试
    - 运行维护
- 适用场景
    - 用户需求不明确
    - 快速捕捉用户需求
    - 若干次原型之后，需求应该手链
    - 大型软件难以设计原型
- 常见途径
    - 模拟最终效果原型界面
    - 真正开发一个原型程序
        - 这种可能后面直接扩充修改完成最终软件
    - 使用类似软件比较
- 分类
    - 抛弃型原型
        - 确认需求之后，原型就直接抛弃不再使用
    - 演化型原型
        - 确认需求后，不断补充完善，最终成为完整软件

#### 螺旋模型

- 将原型模型与软件生命周期结合
    - 也就是使用，演化型原型
    - 并加入风险评估与评审
- 把开发流程分为多个阶段
    - 目标设定
        - 对本阶段进行需求分析
        - 指定专门的目标和开发计划
    - 风险分析
        - 识别本阶段可能存在的风险以及应对措施
    - 开发与验证
        - 进行原型开发与测试
    - 评审
        - 决定是否进入下一个迭代
- 生命周期
    - 需求分析
    - 系统设计
    - 程序设计
    - 原型开发
    - 编码实现
    - 单元测试
    - 集成测试
    - 系统测试
        - 一个迭代测试完成之后
        - 完成本阶段目标之后
        - 就可以进入下一个阶段的，需求分析
    - 运行维护
        - 最终，指导将所有用户需求完成
        - 完成运行维护
- 特点
    - 强调风险分析
    - 支持面向规程说明、面向过程、面向对象开发方法
    - 适用于庞大、复杂、高风险系统
- 优点
    - 抵御风险能力强
    - 支持需求变化
- 缺点
    - 周期长
    - 管理难度大
    - 对开发人员风险分析能力要求高

#### 敏捷方法

> 当下最常用的开发方法，Scrum 敏捷开发框架

- 总体目标
    - 尽早交付
    - 持续交付
    - 高价值优先
    - 客户满意
- 通过加入灵活性，使得用户能够在后期增加或改变需求
- 适用场景
    - 团队、项目规模较小
- 特点
    - 强调适应性
    - 面向人而非过程
        - 面对面交流
    - 增量迭代开发

##### Scrum 敏捷开发框架

- 核心
    - 大项目拆成短周期，快速交付、持续调整
- 基本角色
    - PO(Product Owner)产品负责人
        - 定需求、排优先级
    - SM(Scrum Master)敏捷教练
        - 保障流程、扫清障碍、不做管理
    - DT(Development Team)开发团队
        - 跨职能、自组织，负责交付软件
- 核心工件
    - 产品代办列表（需求列表，Product Backlog）
        - 按照价值排序的需求列表
        - 包含所有需要实现的功能、改进、修复
    - Sprint代办列表（故事列表，Sprint Backlog）
        - 本轮要完成的任务
    - 增量（Increment）
        - 每个Sprint结束时，可交付、可运行的产品版本
- 核心事件
    - Sprint（迭代）
        - 固定周期，一般为2-4周
    - Sprint计划会
        - 确定本轮要做什么、怎么做
    - 每日站会
        - 15分钟内同步
        - 昨天做了啥，有啥阻碍，今天做啥
    - Sprint评审会
        - 演示可运行工作成果，手机反馈
    - Sprint回顾会
        - 总结本轮问题，改进下一轮

#### 统一过程（RUP）

- 用例驱动(UML 用例图)，体系结构为中心，增量迭代开发的过程
- 迭代将软件开发划分为多个项目
- 每个项目划分以下几个阶段
    - 初始阶段
        - 定义最终产品视图、业务模型，确定系统方位
    - 精化阶段
        - 确定系统体系结构、指定工作计划和自愿要求
    - 构建阶段
        - 构造并持续演进
    - 移交阶段
        - 产品发布
- 核心工作流（RUP）
    - 业务建模
    - 需求
    - 分析与设计
    - 实现（编码与单元测试）
    - 测试（集成测试、系统测试）
    - 部署
    - 配置与变更管理
    - 项目管理
    - 环境

### 软件能力成熟度模型(CMMI)

- 从软件开发过程的角度
- 主要用于指导软件开发过程的改进刚和进行软件开发能力的评估标准
- 标准定义
    - 初始级
        - 过程随意、混乱
        - 组织的成功依赖于人员能力和个人英雄主义
        - 能够成功产出产品与服务
        - 常常超出预算
        - 3-5个人小团队，全靠某个人
    - 已管理级
        - 组织要确保策划、文档化、执行、监督和控制项目级的过程
        - 需求为过程建立明确目标
        - 能实现成本、进度、质量等目标
        - 项目级别的，整个企业还是混乱的
    - 已定义级
        - 企业能够根据自身页数情况定义涉河自己的标准流程
        - 将这套体系与流程制度化
        - 同时进行项目积累、企业资产收集
        - 企业级别的，也可以细化到项目级别
        - 中小型企业，基本都是泽哥级别
    - 量化管理级
        - 简历了产品质量、服务质量及过程性能的定量目标
        - 每个项目都能够进行定量的指标衡量的
    - 优化级
        - 通过增量式的与创新式的过程与技术改进
        - 不断改进过程性能
        - 自我优化的
- 层次结构，自顶向下排列
    - 顶层方针
    - 过程文件
    - 规程文件
    - 模板文件

### 净室软件工程

- 一种理想化的，没落地的
- 以经济方式生产高质量软件的工程技术
- 理念在于通过严格的工程过程，在规约和实际阶段消除错误
- 并以净的方式制作软件
- 强调
    - 开发过程中正确性的需求
    - 避免依赖高昂的错误消除过程
- 是在代码增量积聚时进行统计质量验证
- 提倡开发者不需要进行单元测试
- 而是进行正确性验证和统计质量控制
- 主要是基于函数理论和抽样理论
- 技术手段
    - 统计过程控制下的增量式开发
    - 基于函数的规范与设计
    - 正确性验证
    - 同级测试和软件认证

### 基于构件的软件工程(CBSE)

- Component Based Software Engineering
- 基于构件组装的软件开发过程，需要考虑构建的复用、裁剪、适配
- 构件
    - 一个独立的软件单元，可以与其他软件构成一个软件系统
    - 特征
        - 可组装性
        - 可部署性
        - 文档化
        - 独立性
        - 标准化
    - 组成
        - 接口、使用信息、部署
- 认为一个软件是可以被一系列的构建构成的
- 基于构件构建软件的方法
- 主要过程
    - 系统需求概览
    - 识别候选构件
    - 根据发现的构建修改需求
    - 体系结构设计
    - 构建定制与适配
    - 组装构件
    - 创建系统
- 组装方法
    - 顺序组装
        - 直接按照顺序组装
    - 层次组装
        - 依赖组装
    - 叠加组装
        - 多个组件合并抽象为一个组件
- 不兼容形式
    - 参数不兼容
        - 参数类型、数量不一样
    - 操作不兼容
        - 能力一样，单数接口名不一样
    - 操作不完备
        - 不能完全满足使用，缺少接口
- 实现
    - Java EE
        - EJB
        - Servlets 和 JSP
        - JMS(Java Message Service)
        - JDBC
    - Windows COM组件
        - 实际上是虚函数指针

### 需求的定义

- 是系统或部件要满足合同、标准、规范或其他正式文档
- 所需具有的条件或权能
- 分类
    - 业务需求
        - 反映甲方对系统高层次的目标要求
    - 用户需求
        - 用户使用产品必须要完成的任务，是用户的产品预期
    - 功能性需求
        - 为了满足用户的预期而必须实现的内容
    - 非功能能行需求
        - 一些操作、行为、规定、界面、性能、安全等方面的要求

### 需求工程的定义

- 用工程化的思想处理需求
- 划分阶段
    - 需求获取
        - 通过与用户交流或者实际考察，对现有工作模式进行分析
        - 从而开发、捕获、修订用户的需求
    - 需求分析
        - 建立概念模型，作为需求的抽象描述
        - 并尽可能多的捕获显示世界的语义
    - 形成需求规格（需求文档化）
        - 按照相关标准，生成需求描述文档，作为后期开发指南
        - 一般就是需求规格说明书
        - 一般是用例、数据字典
    - 需求确认与验证
        - 以需求规格说明书为输入
        - 通过用户确认、复审会议、符号执行、快速原型等方法
        - 确认和验证去求规格的完整性、一致性、可测试性、可行性
        - 包括有效性检查、一致性检查、可行性检查、确认可验证性
        - 确认需求是否理解错误、是否缺失等
    - 需求管理
        - 包括需求文档的
            - 追踪管理
            - 变更控制
            - 版本控制
- 经过评审批准后的最终文档
- 定义了开发工作的需求基线（baseline）
- 是产品功能性与非功能性需求的一个约定（agreement）

### 需求获取

- 是开发者与用户之间为了定义新系统进行的交流
- 需求获取是获得系统必要的特征，或获得用户能接受、必须满足的约束
- 基本步骤
    - 开发高层的业务模型
        - 理解行业的总体业务模型
    - 定义项目范围和高层需求
    - 识别用户角色和用户代表
        - 与用户交互的边界，人，物，三方系统
    - 获取具体需求
    - 确定目标系统业务工作流
    - 需求整理与总结
- 获取方法
    - 用户面谈
    - 需求专题讨论会
    - 问卷调查
        - 吃力不讨好，不常用
    - 现场观察
        - 实地考察，参与业务，理解业务流程
    - 原型化方法
    - 头脑风暴
        - 游戏开发行业

### 需求管理

- 是对需求变更、了解、控制的过程
- 一旦形成需求文档初稿，就开始了需求管理活动
- 主要内容
    - 变更控制
        - 建议变更
            - 提出变更需求
        - 分析影响
            - 分析带来的影响，需求变更委员会
        - 做出决策
            - 做出最终的决定
        - 交流
        - 合并
        - 测量需求稳定性
    - 版本控制
        - 确认需求文档版本
        - 确认单个需求文档版本
    - 需求跟踪
        - 定义对其他需求的连接链
            - 需求之间的依赖关系
        - 定义对其他系统元素的连接链
            - 设计、编码、测试的关系
    - 需求状态跟踪
        - 定义需求状态
            - 定义、评审、澄清、设计、开发、测试、上线、归档、撤销
        - 跟踪需求每一个状态

### 需求变更

- 需求常常都是会发生的，是不可避免的，但必须是受控的
- 主要内容
    - 仔细评估已建议的变更
        - 进行需求评审、确认
    - 选择合适人员评估变更
        - 需求提出人、负责人
    - 变更应及时通知相关人员
        - 需求干系人，提出人，负责人，开发人员等
    - 按一定流程处理变更，对变更的过程和状态进行控制
- 控制过程
    - 识别问题
    - 问题分析和变更描述
        - 是否超出项目范围
    - 变更分析和成本计算
        - 经济上、成本上、技术上
    - 变更实现
    - 修改后的需求
- 变更策略
    - 所有变更必须遵循变更控制流程
        - 不能想怎么干怎么干
    - 未获批准的变更，不应做设计和实现工作
        - 直接程序员干了，谁也没通知，这不合规
    - 变更应该由变更控制委员会决定实现
    - 项目风险承担者应该能够了解变更的内容
    - 决不能从配置库删除或修改稿变更请求的原始文档
    - 每一个集成的需求变更必须能跟踪到一个经核准的变更请求
        - 实现需要能追溯到需求
- 执行机构
    - 变更控制委员会（CCB）

### 需求追踪

- 包括编制每个需求统系统元素之间的联系文档
- 元素包括
    - 其他需求
    - 体系结构
    - 其他设计部件
    - 源代码块
    - 测试
    - 帮助文件和文档
- 是整个项目的工件之间形成的，水平可追踪性
- 形式
    - 正向跟踪
    - 逆向跟踪
- 合称，双向跟踪
    - 通过建立需求跟踪矩阵来实现
- 垂直可追踪性
    - 也就是需求的版本可追踪性，2版本到1版本

### 软件测试概述

- 使用人工或者自动的手段来测定软件系统的过程
- 目的，在于检验是否满足规定的需求，确认世界结果是否满足预期结果
- 简单说，找有没有BUG，或者有没有不符合需求的结果
- 按执行状态分
    - 静态测试
        - 代码走查，静态代码扫描，findbugs
    - 动态测试
        - 设计驱动程序、桩模块进行实际调用测试
- 按是否测试内部分
    - 黑盒测试
    - 白盒测试
    - 灰盒测试
- 按执行方式分
    - 人工测试
    - 自动化测试
        - AI测试发展趋向
- 软件调试
    - 定位并修复已经发现的缺陷
    - 基本原则
        - 先测试，后调试
            - 测试发现了问题才有调试，没问题，那还调试什么
    - 对比指标
        - 目标
            - 测试
                - 发现软件中可能存在的BUG
            - 调试
                - 发现并修复已经发现的缺陷
        - 执行主体
            - 测试
                - 测试、开发人员
            - 调试
                - 开发人员
        - 过程特点
            - 测试
                - 有预设流程、已知条件、预期结果、可规划进度
            - 调试
                - 从未知问题触发，过程不可预估，难以确定时长
        - 结果
            - 测试
                - 找出错误现象
            - 调试
                - 找出错误的根源并修正代码

### 软件测试方法

#### 黑盒测试（功能测试）

- 也称为，功能测试
- 在完全不考虑内部结构和特性的情况下
- 测试软件的额外部特征
- 测试方法
    - 等价类划分
        - 将程序的输入域划分为若干等价的类
        - 从每个等价类中取出一个代表性数据作为测试用例
        - 比如，数值型输入，合法输入范围去一个，不合法输入范围取一个
    - 边界值分析
        - 往往变成，最容易在边界上发生错误
        - 比如，小于，小等于，可能会写错
        - 比如，及格线60分，那么可选选择59，60，61这三个边界上的作为输入
    - 错误推测
    - 因果图
        - 关注输入条件组合及其约束关系
    - 判定表
        - 适合描述在多个逻辑条件取值组合锁构成的复杂情况下
        - 分别应该执行哪些不同的操作

#### 白盒测试

- 也称为，结构测试
- 根据程序的内部结构和逻辑来设计测试用例
- 对程序的路径和过程进行测试，检查是否满足设计要求
- 测试方法
    - 逻辑覆盖
        - 语句覆盖
            - 一组测试数据，用于保证每条语句都至少执行一次
            - 很弱的逻辑覆盖
        - 判定覆盖
            - 一组测试数据，用于保证每个判断条件，都至少进行一次真一次假判定
            - 针对的最判定，也就是每一个逻辑值，如果在if中有两个判定，则两个判定都应该检查
        - 条件覆盖
            - 一组测试数据，每个逻辑条件的各种取值至少执行一次
            - 也就是if这种，if其中and/or是不考虑全部覆盖的
            - 条件覆盖和判定覆盖没有谁包含谁的关系，两者没有比较性
        - 路径覆盖
            - 一组测试数据，每个可能运行的路径都至少执行一次
            - 比较强的覆盖，但是可能部分组合条件中，无法真正覆盖所有条件组合
    - 循环覆盖
    - 基本路径测试

#### 测试自动化

- 以自动化（脚本）技术来生成测试用例、执行测试
- 主流类型
    - 脚本驱动
        - 脚本分类
            - 线性脚本
            - 结构化脚本
            - 共享脚本
            - 数据驱动脚本
            - 关键字驱动脚本
    - AI程序驱动

### 软件测试步骤

- 软件测试针对的是软件开发全过程，而不仅仅是针对编码

#### V 模型

- 验收测试（确认测试）
    - 针对，需求建模
- 系统测试
    - 针对，概要设计，也针对一些需求建模
- 集成测试
    - 针对，详细设计，也针对一些概要设计
- 单元测试
    - 针对，编码，也针对一些详细设计

#### 分类

##### 单元测试（模块测试）

- 也称为，模块测试
- 在模块编写完成后进行
- 侧重于模块内部的逻辑和数据结构
- 测试内容
    - 模块结构
    - 局部数据结构
    - 重要执行路径
    - 出错处理
    - 边界条件
- 核心部分
    - 驱动模块
        - 模拟被测模块的调用方
    - 桩模块
        - 模拟被测模块的依赖方

##### 集成测试

- 按照系统设计，将模块组合起来进行测试
- 逐步添加模块，直到完成所有所需模块集成
- 一般使用黑盒测试，也有灰盒测试
- 主要方法
    - 自顶向下
        - 下层模块使用桩模块替代
    - 自底向上
        - 上层模块使用驱动模块替代

##### 系统测试

- 将软件与硬件、网络等因素结合住在一起进行的的各种集成测试和确认测试
- 测试内容
    - 回归测试
        - 确认修正的BUG没有问题
        - 一般在回归之前，需要先进行冒烟测试
            - 典型用例测试，不进行完整测试
    - 性能测试
        - 负载测试
            - 不同请求压力的时候的负载情况，最高稳定运行
        - 压力测试
            - 达到什么时候开始崩溃，运行的极限
    - 部署测试

##### 验收测试（确认测试）

- 验收是否满足用户需求或签订的合同
- 分类
    - alpha测试
        - 用户在开发者所在的开发受控环境进行
        - 开发者观看用户操作，记录问题
    - beta测试（客户验收测试）
        - 在部署到的用户场所进行，开发者不在场
        - 用户实际使用后，通过测试报告反馈给开发者

#### 其他类型测试

##### 强度测试

- 系统可运行不崩溃的最小资源

##### 并发测试（容量测试）（QPS）

- 确定系统可处理的最大并发用户数

##### AB测试

- 制作多个版本，同一时间让不同用户体验，收集体验反馈，选出好的版本，正式采用

##### 链接测试

- 确保WEB页面中的链接是有效的，正确链接，不出现404

##### 表单测试

- 确保WEB页面中的表单都能够正常运行提交，校验规则，默认值等

### 软件复杂度度量（环路复杂度，McCabe度量）

- 程序中的选择与循环是主要增加程序复杂性的关键因素
- 程序环路复杂度=弧数-节点树+2*强联通分量数
- 节点
    - 就是每条程序语句
- 弧
    - 就是语句之间的流转关系
- 强联通图
    - 从任意一个节点，都能够找到其他节点
    - 这样的图，就是强连通图
- 强联通分量
    - 增加弧的数量，使得图成为一个强连通图

## 软件维护

### 软件维护的内容

- 分类
    - 正确性维护
        - 指改正对测试阶段尚未发现的错误
        - 不可能测试完所有的BUG
        - 提供补丁
    - 适应性维护
        - 为适应信息技术变化和管理需求变化而进行的修改
        - 新技术、新框架、新硬件、新操作系统等
    - 完善下维护
        - 扩充功能和改善性能而进行的修改稿
        - 增加系统分析设计阶段没有的功能、性能特性
        - 交付后增加功能，用新算法替换提升性能
    - 预防性维护
        - 改进可靠性、可维护性
        - 为了适应未来的软硬件变化
        - 主动增加的预防性的新功能
        - 支持水平拓展

### 遗留系统的处理

- 采用技术水平x业务价值的四维分析象限
    - 技术水平高，业务价值高
        - 改造策略
        - 实际情况是保留不动
    - 技术水平高，业务价值低
        - 集成策略
        - 直接集成就行
    - 技术水平低，业务价值高
        - 继承策略
        - 保留业务逻辑，使用新技术重写，完成技术换代即可
    - 技术水平低，业务价值低
        - 淘汰策略
        - 没价值，直接丢弃
- 系统转换与交接
    - 方式
        - 直接切换
            - 停止旧系统，新系统立即运行，无过渡阶段
            - 省人力和费用，但是风险高
                - 可能新系统有的问题测试覆盖不到，但却很影响业务
            - 适用于新系统不太复杂，或现有一同完全不能用的情况
        - 并行转换
            - 新系统与现有系统并行运行一段时间
            - 试运行结束之后再切换
            - 首先以旧系统为正式作业，旧系统核对使用
            - 经过一段时间，新系统稳定之后在切换
            - 风险小，人力费用小耗大
                - 意味着，业务使用人员需要同时操作两个系统
                - 成倍的工作量
                - 另外，为了保证业务的连续性，往往需要多次数据迁移同步工作
        - 分段转换
            - 直接转换与并行转换的结合
            - 采用分期分批逐步转换
            - 可以按照功能、部门、机器等进行维度进行分批转换
            - 适用于比较大的系统，或旧系统比较稳定，能适应业务需要
            - 或转换风险大
            - 震动小，用户容易接受，但周期更长，人力费用小耗更大
                - 往往涉及到更多的人员参与或者工作量
                - 同时为了保证数据迁移之后的业务一致性或者连贯性
                - 也需要更多的数据迁移成本

### 文档管理

- 文档是软件可维护性的决定因素，必须完整、准确
- 维护阶段对软件的任何修改都必须反映在用户文档和系统文档中
- 分类
    - 用户文档
        - 描述系统功能和使用方法，并不关心技术实现
    - 系统文档
        - 描述系统设计、实现、测试等各方面的内容
