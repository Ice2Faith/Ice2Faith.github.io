## 系统设计概述

- 目的，是根据系统分析的结果，完成系统构建
- 包括
- 概要设计
- 详细设计
-

### 概要设计（系统整体结构设计）

- 又称系统结构设计
- 主要是将系统的功能需求分配给软件模块
- 确定模块的功能和调用关系
- 形成软件的模块结构图
- 即系统结构图
- 一般是，划分子系统，子模块，一般就到这一层

### 详细设计

- 将系统开发的总任务分解为多个基本的、具体的文物
- 为每个具体任务选择适当的技术手段和处理方法的过程
- 需要结合功能性需求和非功能性需求
- 包括
    - 网络设计
    - 代码设计
    - 输入输出设计
    - 处理流程设计
    - 数据存储设计
    - 用户界面设计
    - 安全与可靠性设计

## 结构化分析

- 结构化方法
    - 是一种面向数据流的软件开发方法
    - 以数据流为中心构建软件模型
    - 也就是分析数据的来源、加工、去向
    - 依据此进行设计开发实现
- 机构化分析方法，给出一组帮助系统分析人员产生功能规约的原理与技术
- 利用图形表达用户需求
- 常用的是
    - 数据流图（DFD）
        - Data flow diagram
    - 数据字典
- 分析步骤
    - 分析业务情况
        - 做出反应当前物理模型的DFD
    - 推到出等价的逻辑模型的DFD
    - 设计新的逻辑系统
        - 生成数据字典和基元描述（对字典的辅助描述）
    - 建立人机接口
    - 确认各种方案的成本和风险等级
    - 选择一种方案
    - 建立完整需求规约

### 数据流图（DFD）

- DFD建模方法（过程建模、功能建模）
- 也叫做，过程建模、功能建模
- 步骤
    - 首先，抽象出具体应用的主要业务流程
    - 然后，分析输入，数据从哪来，经过什么加工，去向哪里，变成了什么，最终得到什么结果
    - 通过对系统业务流程的层层追踪和分析，把要解决的问题清晰展现及描述出来
        - 逐层细化
    - 为后续工作打下基础

#### 基本组成元素

- 数据流
    - 表示数据的流向
    - 图形表示
        - 用一个箭头描述数据的流向
        - 箭头上可以标注信息说明或者数据项
        - 从来源指向去处
- 处理/加工
    - 表示对数据进行的加工和转换
    - 图形表示
        - 矩形框，有的也用原型，或者带标题的圆角矩形
        - 指向的数据流为输入数据流
        - 离开的数据流为输出数据流
- 数据存储
    - 表示用数据库、文件形式，存储数据
    - 图形表示
        - 仅包含上下框线的矩形（平行线），或者无右侧框线的圆角矩形（C）
        - 指向的数据流表示存入
        - 离开的数据流表示取出
- 外部项
    - 也称为数据源、数据终点
    - 描述系统数据的提供者或者数据的使用者
    - 一般是系统边界，比如人员、三方系统
    - 图形表示
        - 圆角框，或者平行四边形

#### 层次结构

- 顶层图（上下文关系图）
    - 又叫，上下文关系图
    - 只有一个加工
    - 代表整个软件系统
    - 描述了软件系统与外界之间的数据流
    - 与系统边界的数据关系，人和三方系统
- 0层图
    - 顶层图中的加工经过分解后的图
    - 一般就是主要的几个大的加工
    - 比如：采购、审批、发货
- 底层图
    - 处于分成数据流图中，最底层的图
    - 加工不可再被分解
    - 也就是能够很清楚的表达了，已经能够直接进行编码
- 中间层
    - 只有有一个加工还能被分解的子图
    - 比如，审批还是很复杂，就可以再拆开加工

#### 数据平衡原则

- 识别DFD图的正确性
- 原则
    - 父图中描述过的数据流必须在相应的子图中出现
        - 父图中的数据，如果子图中没有
        - 那只能说系统要么根本不需要这个数据，父图画错了，可能性不大
        - 要么说明，子图画的不正确，把数据弄掉了，可能性最大
        - 子图中，可以有中间的数据流
    - 一个处理至少有一个输入流和一个输出流
        - 一个加工，只有输入或者只有输出，那加工的意义是什么
        - 光输入不输出，浪费资源吗，这是黑洞
        - 光输出不输入，用爱发电吗，这是奇迹
    - 一个存储必定有输入的数据流和输出的数据流
        - 实际绘制的时候，有一些区别
            - 只要保证至少有一个输入或输出即可
            - 有的本来就是只读的
        - 如果是检查正确性，按照实际的来
        - 如果是默写原则，那就按照理论写
    - 一个数据流至少有一段时处理端
        - 处理，就是程序，一个数据想要变动、转换，就需要有程序来运作
        - 否则数据不会平白无故发生变动、转换
    - 模型图中表达和描述的信息是全面、完整、正确、一致的
        - 一个加工，能够产生与输入不同领域的数据，这是不可能的
        - 比如输入只有药品名称，给出股票价格逻辑上就不太行
            - 至少得需要药品公司信息等额外信息才能够找到股票信息
            - 输入信息不足，这是灰洞
- 问题
    - 奇迹
        - 处理，只有输出，没有输入
    - 黑洞
        - 处理，只有输入，没有输出
    - 灰洞
        - 处理，输入的信息，不足以产生输出

#### 数据字典

- 指对数据的数据项。数据结构、数据流、数据存储、处理逻辑等进行定义和描述
- 目的，对数据流图中的各个元素给出详细的说明
- 分类
    - 数据项（字段、表的列）
        - 对图中数据块的数据结构中数据项的说明，是不可再分的数据单位
        - 数据项描述={数据项名、含义说明、别名、类型、长度、取值范围、取值含义、与其他项的逻辑关系（约束）}
            - 比如：姓名项={姓名，表示用户性姓名，无，字符串，300，无限制，无，无}
    - 数据结构（实体类、结构体、视图）
        - 对图中数据库的数据结构说明，反映数据之间的组合关系
        - 构成
            - 可以由多个数据项或数据结构构成
            - 也就是，一个实体类，可以是普通字段，也可以是其他实体类字段
        - 数据结构描述={数据结构名，含义，组成：{数据项或数据结构}}
            - 比如：用户信息={用户实体，表示用户信息，组成：{编号、姓名、状态、角色}}
    - 数据流（请求、调用）
        - 对图中流线的说明，是数据结构在系统内的传输路径
        - 数据流描述={数据流名，说明，来源，去向，组成：{数据结构}，平均流量，高峰流量}
            - 比如：登录数据流={登录数据流，包含用户登录信息，登录界面输入，登录验证控制器，组成：{登录信息结构}，10,300}
    - 数据存储（文件、数据库）
        - 对图中数据库的存储特性说明
        - 是数据结构停留或保存的地方，也是数据流的来源和去向之一
        - 数据存储描述={数据存储名称，说明，编号，流入数据流，流出数据流，组成：{数据结构}，数据量，存取方式}
            - 比如：日志存储={日志存储，存取日志，1.1,接口日志信息数据流，接口日志信息数据流，组成：{接口日志信息}，1000，文件}
    - 处理过程（业务服务，service）
        - 对图中功能块的说明，是处理过程的说明性信息
        - 处理过程描述={处理名，说明，输入：{数据流}，输出：{数据流}，处理：{简要说明}}
            - 比如：登录验证控制={登录验证处理，进行登录验证，输入：{登录数据流},输出：{登录结果数据流，接口日志信息数据流}，处理：{验证登录，记录接口日志，并返回验证结果}}
            - 注意，在高级中，这里的处理，通常表示的是非功能性需求
                - 在中级中，一般就是功能性需求

### 小结

- 理解用户需求
- 画出顶层图，确定系统边界
- 自顶向下，逐步细化，画出各层DFD图
- 定义数据字典

## 结构化设计

### 基本概念

- 定义
    - 是一种面向数据流的设计方法
    - 以分析阶段产生的DFD图和数据字典登文档为基础
    - 自顶向下、逐步细化、模块化的过程
- 基本思想
    - 将软件设计看做是由相对独立且功能单一的模块构成的结构
- 阶段
    - 概要设计
    - 详细设计

#### 模块与模块化

- 模块
    - 将系统划分为模块，模块是组成系统的基本单位
    - 系统中任何一个处理，都可以看做一个模块
    - 特点
        - 只有组合、分解、变换
- 模块化
    - 模块一般具有功能、逻辑、状态三个基本属性
    - 还具有
        - 外部特征
            - 指模块名、参数表、造成的影响（也就是主要功能）
        - 内部特征
            - 指模块的实现代码以及内部使用的数据
    - 外部环境只需要只要外部特征即可
        - 也就是最少知识原则
    - 模块化，通常先确定外部特征，再确定内部特征
        - 也就是先抽象，再实现，逐步细化的过程

#### 信息隐藏与抽象

- 信息隐藏
    - 采用封装技术，将模块实现细节隐藏，使得模块对外尽量简单
        - 模块暴露的少，模块自身修改时，也更加方便可控
- 抽象
    - 抽取食物的基本特征（字段）和行为（函数），忽略非本质的细节（业务无关属性）

#### 灵活性、可移植性

##### 耦合

- 模块之间相对独立性的度量
- 表示模块之间互相连接的紧密程度
- 理想的应该是转换为前三种耦合
    - 但是，在一些设计中，就是需要反规范化设计，来加速交互速度
    - 特别是和底层交互的时候
- 等级，由低到高排列
    - 无直接耦合
        - 无直接关系，相互不传递任何信息
        - 不相干
    - 数据耦合
        - 存在调用关系，传递的是简单的数据值
        - 传递基本数据类型
    - 标记耦合
        - 传递的是数据结构
        - 传递结构体、对象这种非基本数据类型
    - 控制耦合
        - 传递的是控制变量，也就是这个变量会导致模块内部有选择的执行某一个功能
        - 比如，根据用户类型，执行不同的登录逻辑
    - 外部耦合
        - 通过软件之外的环境连接
        - 比如，环境变量，文件，管道
    - 公共耦合
        - 也叫做，特征耦合
        - 通过一个公共的数据环境相互作用
        - 比如，全局变量，共享变量，共享内存
    - 内容耦合
        - 直接使用领一个模块内部数据，或非正常入口转入另一个模块
        - 比如，模块内的静态变量，或者直接goto，强行反射调用，new对象也算

##### 内聚

- 对模块内部元素之间结合的密级程度的度量
- 理想是高内聚，内聚程度越高越好
- 等级，由低到高排列
    - 偶然内聚
        - 处理元素之间没有任何联系
        - 比如，这种utils工具模块，一般就是这种
    - 逻辑内聚
        - 在执行逻辑上像是的功能，通过参数确定执行哪一个
        - 比如，策略模式，根据用户类型决定登录那个
    - 时间内聚
        - 需要同时执行的动作组合到一起
        - 比如，发送通知，会发送各种类型的，邮箱，短信，等等
        - 典型的，发送订阅模式，监听者模式
    - 过程内聚
        - 完成多个任务，必须按照指定过程进行
        - 比如，模板方法
    - 通信内聚
        - 所有元素都在同一个数据结构上操作
        - 或者处理使用相同的输入数据
        - 或产生相同的输出数据
        - 比如，GDI绘图都在一个DC上绘制
    - 顺序内聚
        - 必须按顺序执行，前一个的输出是下一个的输入
        - 比如，常见的业务逻辑都是如此
    - 功能内聚
        - 最强内聚，所有悬殊必须共同作用，才能完成，缺一不可
        - 比如，常见业务逻辑

##### 目标

- 高内聚，低耦合

### 结构化概要设计

- 不常用
- 指将结构化分析产生的DFD图映射为系统结构图（模块结构图）

#### DFD图分类

- 变换型DFD
    - 对应映射叫做，变换分析
    - 数据流的变换
    - 比如，AGI，图片处理
- 事务型DFD
    - 对应映射叫做，事务分析
    - 数据流的状态不同，触发不同的事务处理
    - 比如，审批流程

#### 系统结构图（模块结构图）

- 又叫，模块结构图
- 反映系统的功能呢实现和模块之间的联系与通信
- 包括模块键的层次结构
- 也就反映了系统的总体结构
- 图形表示
    - 模块
        - 矩形，写出模块名或者处理名
    - 连接有向边
        - 箭头，从驱动模块指向被驱动模块
        - 表示当前模块驱动了哪些模块，依赖了哪些模块
    - 数据流
        - 从数据开始端指向接收端，箭头在接收端，开始断使用小圆圈
        - 以便叫头上附加携带了什么数据
        - 用于在连接有向边上，附加上数据的流转方向
        - 表示，什么数据，从什么模块，抵达什么模块
    - 总结
        - 因此，同时具有有向边，表示依赖
        - 依赖边傍边，至少有一条数据流，表示数据流转

### 结构化详细设计

- 主要任务是设计每个模块的实现算法、所需的局部数据结构

#### 常用工具

##### 图形工具

###### 程序流程图(PFD)

- 应用最广泛
- 优点
    - 结构清晰、易理解、易修改
- 缺点
    - 只能描述过程，不能描述数据
- 图形表示
    - 处理
        - 矩形框
    - 分支
        - 菱形
        - 分支时的连接线上需要标注是否，T/F
    - 连接线
        - 有向箭头
    - 起点
        - 空心圆形
    - 终点
        - 实心圆形，或者是带描边的实心圆形

###### 盒图（NSD，方框图）

- 也称，方框图
- 优点
    - 不能任意转移控制
    - 易于表现嵌套和层次关系
- 缺点
    - 问题复杂时图形会很大
    - 不方便修改
- 图形表示
    - 采用嵌套矩形框表示程序控制逻辑
    - 上下两个顺序框，表示顺序
    - 矩形框划分为三角、梯形、三角，表示分支
        - 下方每个矩形表示一个分支处理
    - 大矩形右下角分割为小矩形，当型循环
    - 大矩形左上角分割为小矩形，直到型循环

###### 问题分析图（PAD）

- 比PFD更加直观
- 专门用于反映指自顶向下的过程
- 图形表示
    - 采用时间轴方式表达程序总体逻辑
    - 时间轴上的矩形，表示一个处理逻辑
    - 相邻矩形，表示顺序结构
    - 采用锯齿纹矩形，表示分支
    - 采用横向双截棍，表示循环
- 缺点
    - 表示循环能力较弱

##### 表格工具

###### 判定表

- 某个加工的一组动作依赖于多个逻辑条件的取值
- 也就是，当满足一个组合的条件时，才能够达成某个条件
- 采用二维表表示
    - 行头分为条件区与结果区
    - 列头就是所有可能的情况
- 比如，软考通过，就是必须所有科目都及格，任何一个不及格都是不通过
- 再比如，高考志愿，只有当分数满足，且选课满足，部分要求某些科目分数达到指定要求，才能选报
- 缺点
    - 不够直观

###### 判定树

- 是对判定表的一种图形化变体形式
- 优点
    - 更加直观
- 采用树形结构表达条件组合
    - 每一级树都分为满足与不满足的二叉分支
    - 这样，多级树节点就能够表示条件的组合
- 比如
    - 总分数
        - 数学分数
            - 物理分数
- 这样，每种条件满足不满足的结果，都能够直观的表达

##### 语言工具

###### 伪代码（PDL）

- 一种介于自然语言和形式化语言之间的半形式化语言
- 例如
    - IF 信息正确 THEN 转入主页 ELSE 提示失败 ENDIF

#### IPO图

- 用于对整个模块的输入、输出、处理进行描述
- 通常包括以下部分
    - 表头
        - 系统名称
        - 设计人
        - 模块名称
        - 修订时间
        - 上层调用模块
        - 可调用的下层模块
        - 输入
        - 输出
    - 表格主体
        - 一般就是一个PFD程序流程图
    - 脚注
        - 一般是一些辅助性的注释说明

#### HIPO图

- 用于表示多个IPO图之间的调用关系
- 类似模块图或者部署图

### 小结

- 对DFD图数据流进行变换型、事务性分析
- 自顶向下画出各层系统结构图
- 利用工具进行程序流程设计
- 设计IPO图（HIPO图有时也需要）

- 补充DFD图
